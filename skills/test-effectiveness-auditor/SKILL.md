# Test Effectiveness Auditor

審核測試**有沒有抓 bug 的能力**，而不是「有沒有通過」。一個會通過的測試可能毫無價值——它可能在驗證錯誤的行為、可能根本沒斷言到東西、可能一重構就壞。這個 skill 的工作是把這些「看起來有測、其實沒測」的測試揪出來。

## 第一性原理

整個審核圍繞一句話：**測試的可靠性 = 預期值來源的獨立性 + 測試被證明過會失敗。**

- 「預期值來源的獨立性」：assertion 裡的期望值必須來自**需求/規格/手算**，而不是「實作吐什麼就填什麼」。一旦預期值是從實作複製來的，實作錯、測試跟著錯，而且永遠綠燈。
- 「被證明過會失敗」：一個從沒被看過會紅的測試，價值是未知的——它通過，可能是因為程式對，也可能是因為它根本沒在測東西。

所有檢查點都是這句話的展開。報告每一條發現都應該能對應回這兩個地基之一。

## 如何執行

1. **取得變更**：預設審查當前未 commit 的變更與最近幾次 commit。
   - `cd <repo>` 後 `git diff HEAD`（未 commit）、`git diff HEAD~3 HEAD`（最近 3 次，數量可依使用者指定調整）。
   - 從 diff 找出**新增或修改的測試檔**（`*Test.java`、`*Tests.cs`、`*.test.ts`、`test_*.py` 等慣例）。
2. **連同被測對象一起讀**：光看測試無法判斷 oracle 獨立性與層級是否選對。對每個變動的測試，找出它測的那段實作（subject under test）一起讀。
3. **逐項套用下方檢查點**，每一條發現標上嚴重度。
4. **特別檢查 diff 本身**：維護面的污染只有看 diff 才抓得到（見檢查點 ①b）。
5. 輸出**嚴重度分級的逐項發現報告**（格式見最後一節）。

## 檢查點

### ① Oracle 獨立性 — 預期值有沒有被實作污染（地基一）

**①a 生成時污染（新測試）**
預期值是來自需求/手算，還是「複製實作的輸出」？

- 🚩 預期值是一串沒有任何理由說明的 magic number，看起來就是把跑出來的結果貼上去。
- 🚩 註解或測試名稱透露它是「依照現有行為產生的」「characterization / snapshot」卻被當成正確性測試在用。
- ✅ 好的訊號：預期值旁邊有依據（`// 1000 * 1.05 = 1050，稅率見規格 JKO-XXXX`），或預期值是人能獨立驗算的。

**①b 維護時污染（看 diff 才抓得到）**
這是 commit 前最該擋的一種：

- 🔴 同一個 diff 裡，**實作改了**、而且**測試的 assertion 預期值也跟著被改**，卻沒有對應的需求變更或 commit message 說明——高度懷疑是「程式跑出新結果 → 順手把預期值改成新結果讓它變綠」。這等於把新的錯誤焊進測試。
- 要區分兩種改動，**只有後者是紅旗**：
  - 🟢 機械式適配：方法改名、參數順序變、import 路徑變——**沒動到預期值**，安全。
  - 🔴 預期值改動：`assertEquals(1050, ...)` → `assertEquals(1100, ...)`——這是「重新定義什麼叫正確」，必須質問「需求變了嗎？依據是什麼？」

> 審 diff 時的核心動作：**掃描有沒有 assertion 的『預期值那一側』被修改了。** 有的話一定要在報告裡點出來並要求說明依據。

### ② 非空性 — 測試是不是被證明過會紅（地基二）

測試有沒有真的斷言到有意義的東西？

- 🔴 恆真斷言：`assertTrue(true)`、`assertNotNull(new Foo())`（剛 new 出來當然不是 null）、`assert 1 == 1`。
- 🔴 完全沒有 assertion：只呼叫了方法，沒驗任何結果（除非明確是在測「不拋例外」，且有註明）。
- 🔴 自餵自(self-feeding)：斷言在「你自己用 mock/stub 餵進去的回傳值」上。例如 `when(repo.find()).thenReturn(x)` 然後 `assertEquals(x, service.get())`——這只證明了 mock 框架會回傳你設定的值，沒測到任何真實邏輯。
- 🟢 建議(非空性的主動驗證)：對分支多的複雜邏輯，建議跑 **mutation testing**（Java→PITest、.NET→Stryker.NET、JS/TS→Stryker）——故意往實作注入 bug，看測試會不會抓到。抓不到的就是空包彈。這是「親眼看它紅」的自動化替代品。**此 skill 只做靜態判斷與建議，不實際執行 mutation 工具。**

### ③ 測行為，不測結構

斷言的是公開契約（input→output、可觀察的副作用），還是內部實作細節？

- 🟡 測試呼叫**私有方法**、斷言**內部欄位/中間狀態**——這種測試綁死了實作結構，純重構就會壞，是未來重構的負擔，也增加 code review 認知負擔。
- 🟡 把「verify 某個依賴有沒有被呼叫、呼叫幾次、呼叫順序」當成**主要**斷言（interaction testing），而不是驗證最終的可觀察結果。
- 判準：**這個測試能不能在「不改變外部行為的純重構」後原封不動還通過？** 不能的話，它很可能綁錯了層。

### ④ 測在對的層

- 🟡 對一個**編排型/CRUD 型**的單元（Service、JOB：撈資料→算→寫回→打外部）寫「把依賴全 mock 掉、只 verify 互動」的 unit test。這層的「邏輯」幾乎都是接線，mock 一切的 unit test 既脆又沒驗到真正重要的東西（DB 有沒有變成對的樣子、檔案對不對、外部呼叫 payload 對不對）。這種應該用整合/JOB 層測試驗真實副作用。
- 🔴（最隱蔽）**複雜分支埋在 CRUD 流程裡沒被抽出來**，導致只能透過昂貴的 API/JOB 鋪設才能觸發，於是實際上沒被測到——「看起來有測、其實沒測」。發現這種，建議**把複雜邏輯抽成純元件**，讓它可以被便宜地 unit test 窮舉邊界。
- 對照的正確分工：
  - 純邏輯／分支多的演算法 → **unit test** 窮舉邊界（便宜、精準、抗重構）。
  - 編排／CRUD／副作用 → **整合/API/JOB 層測試**驗真實效果。

### ⑤ 邊界／例外覆蓋

分支多的那段邏輯，關鍵邊界有沒有被碰到？

- 檢查：null/空集合、邊界值（0、最大、跨月/閏年）、錯誤路徑、partial failure、idempotency、金額進位捨入、併發。
- 🟡 只有 happy path、沒有任何異常路徑或邊界案例。
- 覆蓋率當**信號**用（看「哪些分支沒被碰」），**不當目標**（追 100% 覆蓋率會產生一堆綁手綁腳又沒用的測試）。

### ⑥ 副作用驗證（針對 IO/整合測試）

- 🟡 對 JOB/Repository 等有副作用的程式，只 mock-verify「有呼叫」，卻沒驗「DB 真的變成對的狀態 / 檔案真的長對 / 外部呼叫帶了對的 payload」。建議用測試用真實 DB（如 Testcontainers）驗最終狀態。

### ⑦ 真實情境貼近度

- 🟢 輸入輸出是否貼近真實使用情境？還是「餵一堆假資料 → 產出一個跟真實情境脫節的無意義結果」？脫節的測試就算通過也驗證不了真實行為。

### ⑧ 測試誠實性 — 宣稱的覆蓋 vs 實際斷言的覆蓋

這是 ④ 的高頻具體形式，但危險性高到值得獨立檢查：**一個「名稱/DisplayName/註解宣稱驗了 X、但 assertion 根本沒驗到 X」的測試，比沒有測試更危險**——它給人虛假的信心，從此沒人會回頭補那個真正的測試。

- 🔴 DisplayName／測試方法名／註解宣稱驗證某行為（例如「交易回滾」「冪等」「重試三次」「並發安全」「快取生效」），但 assertion 沒有任何一條真的驗到那件事。
- **核對方法**：讀測試名稱/DisplayName 聲稱了什麼 → 逐條確認 assertion 真的涵蓋了那些聲稱。聲稱與斷言之間的差距，就是紅旗。
- 常見成因：被宣稱的行為是跨切面／框架行為，在當前測試層級**結構上就驗不到**（見下方「純單元測試盲區」）。
- 建議：要嘛補到能真正驗證的層級，要嘛把名稱/DisplayName 改成只描述「實際驗到的範圍」，不要讓測試文件騙人。

### ⑨ 測試結構與可讀性慣例（專案規範）

這一項不是「抓 bug 能力」的地基，而是**專案強制的測試撰寫慣例**（來源：全域 `CLAUDE.md` → Testing Conventions）。新增或修改的測試若缺這些，一律點出並要求補上：

- 🟡 **缺 `@DisplayName`**：每個測試方法都必須有 `@DisplayName`，且用**中文**描述測試情境與預期結果；類別層級也應有 `@DisplayName` 說明受測對象。
- 🟡 **缺 GIVEN / WHEN / THEN 分段**：測試 body 必須以 `// GIVEN:`、`// WHEN:`、`// THEN:` 三段註解分隔，且每段註解要**簡述該段在做什麼**（不是只放空標籤）；三段之間空一行。
  - GIVEN = 前置條件 / mock 設定；WHEN = 執行受測行為；THEN = 斷言結果。
- 判準：這是格式與可讀性要求，**與 ⑧（誠實性）不同** —— ⑧ 查的是「DisplayName 有沒有說謊」，⑨ 查的是「有沒有依規範寫」。兩者可同時觸發（例如有 DisplayName 但內容與斷言不符 → ⑧🔴；完全沒 DisplayName → ⑨🟡）。

## 純單元測試（Mockito 等）的已知盲區

純 Mockito／無 Spring context 的單元測試，下列行為**結構上驗不到**。看到測試（尤其在 DisplayName/註解裡）聲稱驗了這些就要警覺——這通常就是檢查點 ⑧ 的觸發點：

- **`@Transactional` 回滾** — 沒有真的 transaction manager，mock 測試只能驗「方法被呼叫／有拋錯」，驗不到「資料真的被回滾」。需 service + 真實 DB 整合測試。
- **`@Async` / 多執行緒** — 非同步派發與執行緒切換不會真的發生。
- **AOP 切面行為**（`@Cacheable`、`@Retryable`、`@Validated` 等）— Spring 代理沒被建立，切面邏輯不會觸發。
- **真實 SQL / ORM 映射** — mapper 被 mock 掉，欄位型別映射與 SQL 正確性驗不到（需 `BaseMybatisTest` 之類真 DB 測試）。
- **`@Value` / 設定注入** — 需用反射手動塞值，而這本身會綁死私有欄位名（見檢查點 ③）。

這些不是「測試寫錯」，而是「層級選擇的固有侷限」。重點是：**別在驗不到的層級宣稱驗到了**（⑧），該往整合測試補的就往上補。

## 避免誤報（很重要）

這個 skill 寧可精準也不要狂噴。**不要**把下列當成問題：

- 機械式測試適配（改名、簽章變動、import 調整）——只要**沒動預期值**，不是污染。
- 對純邏輯/util/演算法寫的 unit test——那本來就是 unit test 最該存在的地方，不要因為「測得很細」就批評。
- 沒有 100% 覆蓋率——覆蓋率不是目標。
- 整合測試比較慢——那是它換來真實性的合理代價。

判斷不確定時，**標較低嚴重度並說明你的不確定**，不要硬套紅旗。

## 嚴重度分級

| 等級 | 意義 | 典型案例 |
|---|---|---|
| 🔴 高 | 讓測試**失去抓 bug 能力**、給虛假信心，或正在把錯誤焊進測試 | 維護時改了預期值、恆真/空斷言、自餵自、複雜分支實際沒被測到、宣稱覆蓋但實際沒驗（⑧） |
| 🟡 中 | 削弱有效性或**增加重構/review 負擔**，但仍有部分價值 | 綁內部結構、over-mock 驗互動、層級選錯、只有 happy path、缺 `@DisplayName`／GIVEN-WHEN-THEN 分段（⑨） |
| 🟢 低/建議 | 可優化，不影響當前正確性 | 命名、真實資料貼近度、建議補 mutation testing |

## 報告格式

ALWAYS 用以下結構輸出：

```
# 測試有效性審核

**審查範圍**：<git diff HEAD / 最近 N 次 commit>，共 <X> 個測試檔變動

## 摘要
- 🔴 高 <n> 項｜🟡 中 <n> 項｜🟢 低/建議 <n> 項
- 一句話總評：<這批測試整體可靠嗎？最該先處理的是什麼？>

## 逐項發現

### 🔴 [檢查點編號] <一句話標題>
- **位置**：`path/to/FooTest.java:42`
- **問題**：<具體描述，引用實際的程式碼/diff>
- **違反的地基/原則**：<oracle 獨立性 / 非空性 / 測行為非結構 / 測在對的層 ...>
- **建議**：<具體怎麼改；若是預期值改動，要求說明需求依據>

### 🟡 ...

### 🟢 ...
```

報告每一條都要：**指到檔案行號、引用實際程式碼、對應回它違反的地基或原則、給可執行的修正建議**。沒有發現問題時，明確說「這批測試在 X、Y 面向上是健康的」，不要為了湊數硬找問題。
