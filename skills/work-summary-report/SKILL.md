# 工作總整理報告 (Work Summary Report)

把一個人某段期間的實際產出，從 JIRA 與週報中萃取、去蕪存菁，整理成一份**主管/自己回顧用**的
HTML 報告。這份報告的讀者在乎的是「**這段期間完成了哪些重要工作**」，不是週報式的進度流水帳。

核心心法：**報告是「成果總結」不是「週報」**。凡是「為了週報才存在」的東西（每週進度 %、
第幾週、單項工時）都不該進主軸敘事；凡是「別人做的事」都不該寫進來（這是**本人**的工作紀錄）。

---

## 產出結構（HTML，單一檔、可離線）

固定五區，順序如下：

1. **KPI 卡 + 口徑說明 callout** — 期間完成總數、各領域數；callout 講清楚口徑。
2. **一、重點工作主軸** — 依大主題分組的敘事（本報告的核心價值）。
3. **二、數據分析** — 領域分佈表、類型分佈、每月完成長條圖、Top Epic。
4. **三、逐週時間軸** — RD3 週報逐週摘要（此區**保留**週次，因為它本質就是逐週流水帳）。
5. **四、完整 JIRA 清單** — 期間完成的所有單，可依領域篩選 + 關鍵字搜尋，單號可點開。

用一支**可重跑的 Python 產生器**（`build_report.py`）讀資料檔、產出 HTML。
`assets/build_report_example.py` 是一份完整可參考的實作（CSS、JKO linkify、表格 JS、
長條圖、主軸/子標題/涵蓋徽章結構都在裡面）——**直接拿它改**，不要從零寫。

---

## 資料口徑（最重要，先跟使用者確認）

**只納入「完成時間落在目標期間」的單，不論開單時間。** 這是最關鍵、最容易錯的一點。

- ❌ 不要用「期間內 assignee 曾是我」——那會把長期掛名、早已在往年完成的 backlog 舊單全算進來，
  數字虛胖（實測某次是 639 vs 真正 152）。
- ✅ 用 changelog 判定完成時間：
  ```
  assignee was currentUser() DURING (start, end)
    AND status CHANGED TO ("完成","Done") DURING (start, end)
  ```
  並與「resolutiondate 落在期間」的集合**雙重核對**（正常應零差異；此 JIRA 專案有大量
  「完成」單沒填 resolutiondate，所以 changelog 較可靠）。
- **排除** ICE BOX（擱置，狀態分類雖是 Done 但不是真的完成）、進行中、待處理。
- 期間內可再拆「本期新開立 vs 往年開立、本期結案」兩種，讓 callout 說明白。

**跨期的大專案要誠實標界線**：若某專案的主體開發在往年、本期只做上線/收尾，
要在該主軸講清楚（例：「API 層翻寫與串接於 2025 完成，本期進行灰度上線、切換與舊系統退役」），
避免讀者誤以為整個專案都是本期從零做的。

## 資料蒐集流程

1. 確認**期間**（起訖日）、**使用者 JIRA 帳號**（`accountId`）、**cloudId**、以及**週報位置**
   （RD3 週報為 Confluence 空間 RD3 下的年度頁，逐週為子頁）。
2. **JIRA**：用上面的 JQL 撈完成單。MCP 回傳常因太大被存成檔（超過 token 上限）——
   **用 Python 處理檔案、不要讀進 context**；`pageInfo.hasNextPage` 為真時用 `nextPageToken` 分頁。
   欄位取 `summary,status,issuetype,priority,labels,components,created,updated,resolution,`
   `resolutiondate,parent`。存成 `data/jira_<period>.json`。
3. **週報**：取年度頁的 descendants（逐週子頁），逐頁抓 markdown，**只擷取本人段落**
   （週報是全組共用表格，依姓名欄/區塊定位本人）。量大時**開並行 subagent** 分批處理、
   各自寫檔、回傳精簡摘要，避免塞爆主 context。存成 `data/weekly_*.md`。
4. 編碼：檔案一律 UTF-8（`ensure_ascii=False`）。Windows console 顯示中文亂碼只是
   終端顯示問題，底層資料是好的——跑 Python 前設 `export PYTHONIOENCODING=utf-8`。

## 內容規則

### A. 只寫本人的工作（鐵則）
這份文件是**本人的工作紀錄**。描述只聚焦本人實際做的事：
- **不要**把他人/外部單位的動作算成本人的，也**不要**特別去描述是誰做的（不用寫「PM 協調」「SRE 排查」）。
  例：IP 白名單那次，本人是「發現問題 + 驗證切換結果」，對外協調是 PM 做的 → 只寫發現與驗證，PM 一字不提。
- **動詞要精準**，別無意間攬功：是「發現/驗證/協調/跟進」哪一個就寫哪一個。
  「推動 XX 公司完成切換」若實際只是發現+驗證，就不能用「推動」。
- 排查類事故若 SRE/DBA/DE 也有參與，只留本人的部分（例：「已排除 AP 層；至今未找出根因、暫無解」），
  不要細數別人的排查過程。

### B. 對照 JIRA 正式單名，別信週報簡寫
週報的單號標註**常有錯**（把工作記到錯的 JKO、用看不懂的簡寫）。實測踩過的雷：
「泰安查線」實為「撈取泰安產險交易險種明細」、某段被標到 25569 其實 25569 是別的單、
27897 週報寫「API KEY 過期」實為「調閱國壽 UAT 保單異常 Log」。
→ **主軸引用的每個 JKO，都用其 JIRA 正式 summary 核對一遍**；有出入以正式單名為準。
找不到對應單的工作（週報號碼是錯的、或根本沒開票）先標「單號待確認」並回報使用者確認。

### C. 描述要「一看就懂」
- 講清楚**發生什麼事 / 處理了什麼**，讀者掃一眼要能懂。避免只寫欄位名或代碼
  （「國泰付款方式欄位」→「國泰銷帳 API Request 欄位差異，致付款方式未正確儲存」）。
- **公司內大家都懂的服務名不用解釋**（onlinepay、authpay、UAPI、MinIO 等）——內部讀者，別畫蛇添足。

### D. 排除「週報才需要」的雜訊（主軸區）
主軸只呈現「有哪些重要項目」，以下**一律移除**：
- **完成度百分比**（`30%→35%`、`0%→100%`、「推進至 40%」）——週報進度追蹤用。
- **週次**（`W1–W9`、`W16`…）——主軸不寫第幾週完成。
- **單項工時**（`2.5d`、`1d`、`0.5h`）——不列在主軸；若要呈現工時，放到 JIRA 清單那區。
- 可**保留**的：真實流量比例（灰度 `10%→100%`，這是機制不是完成度）、里程碑日期（`05/27 上線`）、
  專案總長度（「歷時約 2.5 個月」）——這些是規模/事實，不是週報進度。判斷準則：**它是「進度追蹤」還是「客觀事實」**。
- 逐週時間軸（第三區）是週報流水帳，週次**保留**；完成度 % 是否清由使用者定（預設可留在時間軸）。

### E. 涵蓋「沒開 JIRA 票」的工作
重要但沒開票的工作（自建工具/skill、跨團隊協作產出）很容易漏。**主動問使用者**有沒有這類項目。
例：本人自建的「上線驗證 Claude Skill」（做 LOG 正向驗證，補告警抓不到的死角）就沒有 JIRA 票，
但屬重大產出，要列（放在對應主軸 + AI/工具主軸，並註明「自建工具、無 JIRA 票」）。

## 主軸組織規則

- **依大主題（專案/領域）分主軸**，例：保險平台遷移、繳費某專案、捐款維運、叫車、AI 導入。
- **同一主軸內若混了不同性質的工作，用小標題再分組**（例保險：「遷移與翻寫 / 平台強化 / 維運、事故與 RCA」）。
- **明顯是同一件事不同階段的單，合併成一條**（例「手續費月報表」：開發 → 測試重構 → MinIO 串接 → Argo 上線，
  五張單併一行）。
- **不要有「雜項事故」大桶**——事故/維運項目**歸回所屬專案**；跨模組事故按影響拆到各領域
  （例 onlinepay 事故拆「保險端 / 捐款端」）。
- 每個主軸標題掛一個「**涵蓋 N 張完成單**」徽章，讓主軸與總數對得上（讀者才不會覺得
  「開頭數字大、主軸只列幾條」）；主軸底部的「**代表單**」chips 是**精選**、非全部，全部在第四區清單。

## HTML 輸出細節

- **自包含、離線可開**：CSS、JS、資料 JSON 全部內嵌，不依賴外部資源。
- **所有 JKO 單號都是可點連結**（`https://jkopay.atlassian.net/browse/JKO-####`，開新分頁）：
  - 敘事/時間軸/chips：對 `<script>` 之前的可見 HTML 做一次 regex linkify（`JKO-\d+` → `<a>`），
    **不要動內嵌的 JSON**（會壞掉 JS）。
  - 表格：在 client-side render 時對摘要/Epic 欄位做 `linkJko()`，Key 欄本來就是連結、別重複包。
- **可篩選清單**：領域按鈕 + 關鍵字搜尋 + 顯示筆數；跨年結案的單可加小標記。
- 繁體中文、UTF-8。產生器最後**印出關鍵數字**（總數、各領域、涵蓋徽章值）方便自我核對。
- 用 `assets/build_report_example.py` 為藍本改（含完整 CSS/JS/圖表/linkify）。

## 資料夾與檔案衛生

放在 skill 底下**per-period 專屬資料夾**（每半年一次，收在一起好找、可重跑），別散在家目錄：
```
~/.claude/skills/work-summary-report/reports/<period>/     ← 例：reports/2026H1/
├── data/
│   ├── jira_<period>.json           ← JIRA 原始資料
│   ├── completed_<period>_keys.json ← 完成單口徑的 key 清單（產生器讀這個過濾）
│   └── *weekly*.md                  ← 週報本人條目
├── build_report.py                  ← 工作總整理產生器（BASE 指向本資料夾，可原地重跑）
├── <人名>_<期間>_工作總整理.html      ← 工作總整理報告
│   ── 以下為 PEP 模式產物（見「PEP 自評報告模式」）──
├── pep_catalog.py                   ← 職級行為指標目錄（單一真相來源）
├── pep_mapping.json                 ← 可 curate 的佐證映射
├── validate_mapping.py              ← 映射驗證器
├── build_pep_report.py              ← PEP 產生器（輸出下面兩份）
├── _base_style.css                  ← 由工作總整理 <style> 擷取、各報告共用基底樣式
├── <人名>_<期間>_PEP標準自評.html      ← PEP 自評（六職能）＋ Top Two Wins 候選
└── <人名>_<期間>_核心價值.html         ← 核心價值本人事蹟
```
- 產生器 `BASE` 用絕對路徑指向資料夾；若搬移資料夾，記得同步更新各產生器的 `BASE`。
- **清掉所有暫存/中間檔**（`_frag_*.json`、`_evidence_index.json`、`__pycache__`、探查用一次性檔）。過時版本也刪。
- 取捨：個人績效資料會長住 skill 目錄。因這是 `~/.claude/skills/` 下的**個人** skill（非共享 plugin、預設不 commit/同步），私密性可接受；若日後分享此 skill，`reports/` 不要一起帶走。

## PEP 自評報告模式（公司期中/年度績效考評用）

當使用者要產「PEP 自評 / 績效考評自評 / 期中考評 PEP / self-eval 報告」時用本模式——它**建立在工作總整理的同一批已蒐集資料上**（重用 `reports/<period>/data/`），把成果重新映射成公司 PEP 填寫格式，輸出**兩份獨立 HTML**（`PEP標準自評`、`核心價值`，見下）。與工作總整理並存、各自一支產生器、共用 `data/` 與 `_base_style.css`。

**對應公司 Backend PEP Template 的 docx 區塊，拆成獨立 HTML 供回填參考**（這些 HTML 只是回填 docx 的參考素材）：
- **工作項目**（docx 區塊 1）— **不由本模式產出**，直接用「已完成工作總整理」報告（那份的重點主軸即工作項目，避免重複維護）。
- **PEP 標準自評**（docx 區塊 2）→ `<人名>_<期間>_PEP標準自評.html`：對照**六大職能**逐項列「行為指標 + 具體案例」，**每個指標前標出對標標籤「能力名 #編號」**（如 `技術能力 #4`），對應公司 docx 的「對應指標：技術能力 #4「…」」寫法，方便回填、一眼看出案例對標哪項能力；頁內另附 **Top Two Wins 候選**面板——依公司規則（Confluence 2023850012、提交至 feedback.jkopay.app）每件回答**三問「我做的事／對齊目標／改變（具體成果）」**、重影響力不重數量、至多 2 件、每項約 100–200 字。
- **核心價值**（docx 區塊 3）→ `<人名>_<期間>_核心價值.html`：五大核心價值的**本人**事蹟（同組成員觀察由使用者自行補）。
- 總結（docx 區塊 4）由 Team Lead 面談時填 → 本工具不產。

**六大職能 / 五核心價值 / 行為指標**：以 `pep_catalog.py` 為**單一真相來源**（目前為 J3 資深工程師標準，來源 Confluence 1669660766；六職能＝技術能力/領導力與影響力/交付與當責/溝通與協作/業務與策略/AI 素養）。換職級就換 catalog。

**產物與工作流**（都在 `reports/<period>/`）：
- `pep_catalog.py` — 職級六職能指標 + 5 核心價值 + 職能簡稱 `SHORT_NAMES`（對標標籤「能力名 #編號」用）；產生器與驗證器共用。
- `pep_mapping.json` — 可 curate 的佐證映射；指標只帶 `evidence`（`{key, case}`，指標文字在 catalog、避免重複），`key` **可省略**（用於無 JIRA 票的重要工作，如自建工具）。`top_two_wins` 每件為三問結構 `{title, did（我做的事）, goal（對齊目標）, change（改變）, evidence}`。
- `validate_mapping.py` — 驗證結構、指標編號合法、所有帶 key 佐證 ∈ 完成單。改 mapping 後先跑它。
- `build_pep_report.py` — 讀 catalog + mapping + jira 原始資料 → **輸出兩份 HTML**（PEP標準自評、核心價值）；最後印關鍵數字（指標覆蓋 N/總數、核心價值事蹟數、TTW 候選數）自我核對。

流程：
1. 重用 `data/`（完成單 + 週報）。先產一份精簡 `data/_evidence_index.json`（key→summary/type/labels/epic）給 subagent 用。
2. **自動起草 mapping**：開**並行 subagent** 分職能掃 152 完成單 + 主軸敘事（`build_report.py` 內已核對過的 themes/timeline 是最佳來源），各自寫獨立 `_frag_*.json`，controller 合併回 `pep_mapping.json`。規則：只寫本人工作、動詞精準不攬功、**對照 JIRA 正式單名**、內部服務名不解釋、Show don't tell（每指標要具體案例）、寧缺勿濫但使用者若要「盡量列」則放寬。
3. `validate_mapping.py` → `build_pep_report.py`。
4. 逐職能與使用者 curate；**帶人/Code Review/品質把關類指標** JIRA 與週報抓不到，屬正常，留白請使用者自補。

**PEP 專屬內容規則**：沿用工作總整理鐵則（只本人、正式單名、JKO linkify、排除週報雜訊）；自評**不強制**標等級（成長中/穩定展現/超越期望），預設不標，使用者要標再加。**同一項工作可同時對標多個指標**（例：自建 skill 可同時是 AI 素養 #1/#3/#4 與業務策略 #1/#3 的佐證）——重複出現是正常且刻意的，**不要為了去重而刪**；PEP 是能力盤點，同一件事本就能展現不同面向的能力，是否精簡由使用者最後判斷。

## 工作方式（實務提醒）

- **逐條與使用者對焦**：使用者是「誰做了什麼、正確單號」的最終真相來源。描述有疑慮就問，不要猜
  （猜錯很傷信任——實測連續猜錯兩次某項角色）。
- **每次修改後重跑產生器 + 用 Python/grep 驗證**（確認字串有換、無殘留、JSON 仍可解析、
  無殘留 placeholder、連結數正確）。編輯 `build_report.py` 的字串時用唯一子字串精準比對。
